# Меры безопасности: вход, сессия и почта

Понятное описание того, как в «Страже» защищены регистрация, вход и создание ящика. Без живых денег — учебный стенд.

Связанные файлы кода: `src/password_hash.py`, `src/auth.py`, `src/web_app.py`, `src/db_cipher.py`, `src/mail_client.py`, `src/mail_app.py`, `src/store.py`, `src/user_mcp.py`, `src/mcp_url_guard.py`, `entrypoint.py`.

Карта всех гардрейлов (фраза, тул, ответ, MCP): [ГАРДРЕЙЛЫ.md](ГАРДРЕЙЛЫ.md).

---

## Фраза для слайда

> Сначала ящик на почте (Argon2 в SQLCipher); потом регистрация в Страже на ту же почту (пароль может быть другим) — Argon2 и JWT в HttpOnly-cookie.

**Что это значит простыми словами**

1. На странице **почты** создаёте ящик: пароль ящика → Argon2 → зашифрованная `mail.db`.  
2. На странице **Стража** регистрируетесь на **ту же почту**; пароль учётки Стража может отличаться. Учётка пишется в `strazh.db`.  
3. При входе в Страж сверяют пароль Стража с кашей учётки и дают **пропуск** (JWT) в cookie HttpOnly. Вход в почту — своим паролем ящика.

## 1. Пароль только Argon2 (медленно + соль), не plaintext и не голый SHA-256

### Как работает у нас

- Открытый пароль в базу **не пишется**.  
- В таблицах `users` (Страж) и `mailboxes` (почта) лежит строка вида `$argon2…`.  
- При входе сервер вызывает проверку Argon2: «эта каша соответствует тому, что человек ввёл?»  
- Если в базе лежит старый отпечаток SHA-256 без соли — вход **не** открывается. Принимается только хеш, который начинается с `$argon2`.

### Зачем это нужно

| Плохой вариант | Почему плохо | У нас |
|---|---|---|
| Пароль текстом (plaintext) | Украли файл базы — сразу знают пароль | Нет |
| Голый SHA-256 без соли | Быстро подбирается, одинаковые пароли выглядят одинаково | Не принимается |
| Argon2 с солью | Подбор долгий и дорогой; у каждого своя «примесь» | Да |

**Соль** — случайная добавка внутри хеша. Два человека с паролем `Qwerty123!` получат **разные** строки в базе.

**Медленно** — специально: злоумышленнику нужно много времени на перебор, обычному входу хватает доли секунды.

Код: `src/password_hash.py` (`hash_password`, `password_matches`).

## 2. Правило сложности пароля при регистрации

### Как работает у нас

Перед записью в базу пароль проверяют:

- не короче **8** знаков;  
- есть **заглавная** буква;  
- есть **строчная** буква;  
- есть **символ** (не буква и не цифра).

Если правило не выполнено — регистрация не проходит, в базу ничего не пишется. Тот же контроль — при создании почтового ящика.

### Зачем

Слабый пароль (`12345678`, `password`) легче угадать. Правило отсекает совсем простые варианты ещё до сохранения.

Код: `password_hash.validate_password`, вызов из `auth.register` и почты.

## 3. База зашифрована SQLCipher

### Как работает у нас

Файлы `strazh.db` и `mail.db` — не обычный открытый SQLite. Их открывает пакет **sqlcipher3** ключом из переменной **`STRAZH_DB_SECRET`** (не короче 16 символов). Ключ лежит в `data/db_secret`, в репозиторий не коммитится. Права файла базы — `0600` (только владелец).

Без правильного ключа содержимое базы с диска прочитать как текст нельзя.

### Зачем

Даже если кто-то скопировал файл `.db` с компьютера или из тома Docker, без секрета это «каша», а не список паролей и счетов.

Код: `src/db_cipher.py`.

## 4. JWT подписан секретом сервера; cookie HttpOnly; SameSite=Lax

### Как работает у нас

После успешного входа или регистрации сервер делает **пропуск** (JWT) и кладёт его в cookie браузера `strazh_token`.

Внутри пропуска (в закодированном виде):

| Поле | Смысл |
|---|---|
| `sub` | кто вы — ваш email |
| `jti` | номер этого пропуска |
| `exp` | до какого времени действует (около 8 часов) |

Сервер **подписывает** пропуск своим секретом. Подделать «я — lavr@…» без секрета нельзя: подпись не сойдётся.

**HttpOnly** — скрипт на странице (JavaScript) **не читает** cookie. Сложнее украсть пропуск через вредоносный код на странице.

**SameSite=Lax** — cookie в основном уходит на ваш сайт Стража, а не на любой чужой сайт при случайном переходе.

Браузер сам присылает cookie при запросах (`/api/chat`, `/api/account`…). Пользователь токен руками не копирует.

### Зачем

Сессия = «браузер доказал, что это вы», без хранения пароля в cookie и без списка «все онлайн» в виде отдельной сущности на каждый клик.

Код: `auth.issue_jwt` / `session_from_token`, `web_app._set_session_cookie`.

## 5. Выход → jti в revoked

### Как работает у нас

Таблицы «кто сейчас онлайн» нет. Пока у вас в браузере живой пропуск — сервер вас узнаёт.

При **выходе**:

1. сервер читает номер пропуска (`jti`);  
2. записывает его в таблицу **отозванных** токенов (`revoked_tokens`);  
3. стирает cookie в браузере.

Дальше этот же пропуск, даже если кто-то его сохранил, даёт отказ «Сначала войдите».

### Зачем

Вышли с компьютера в аудитории — старый пропуск нельзя использовать снова.

Код: `web_app.api_logout`, `store.revoke_token`, проверка в `session_from_token`.

## 6. Лимит попыток входа по IP

### Как работает у нас

Сервер запоминает неудачные попытки входа с одного IP. Если их слишком много за короткое окно (порядка минуты) — ответ **429**: подождите, прежде чем пробовать снова.

Успешный вход сбрасывает счётчик для этого IP.

### Зачем

Затрудняет подбор пароля «в лоб» (много разных паролей подряд к одному или разным ящикам с одной машины).

Код: `_login_locked` / `_login_failed` / `_login_ok` в `web_app.py`.

## 7. Одинаковый текст ошибки при неверном логине или пароле

### Как работает у нас

И «такого email нет», и «пароль неверный» снаружи выглядят одинаково:

> Неверная почта или пароль.

### Зачем

Злоумышленник не узнаёт, существует ли уже учётка на этот адрес (меньше подсказок для атак).

Код: константа `LOGIN_FAIL` в `auth.py`, ответ 401 при входе.

## 8. Ящик и Страж — разные регистрации; служебный ключ для доставки писем

### Как работает у нас

1. **Публично на почте:** `POST /api/register` — человек сам создаёт ящик (пароль по правилу сложности, лимит попыток с IP).  
2. **Публично в Страже:** `POST /api/register` — только если ящик на эту почту уже есть (`/api/internal/exists` + `STRAZH_MAIL_SECRET`). Пароль Стража свой, с паролем ящика не сверяется. Страж ящик **не** создаёт.  
3. **`STRAZH_MAIL_SECRET`** — ключ служебных вызовов Стража к почте (проверка «ящик есть», доставка писем). Не пароль пользователя и не JWT Стража. Без верного ключа internal API → **403**.

### Зачем

Окна регистрации разделены. Без ящика на почте учётку Стража на этот адрес не завести. Пароли почты и Стража независимы. Служебная доставка писем не открыта без секрета сервиса.

Код: `mail_app.api_register`, `auth.register`, `mail_client.mailbox_exists`, `action_hash.mail_secret`.

## 9. Кастомный MCP не получает ключ почты и не шлёт от имени Стража

Кастомный MCP (кнопка «Мои MCP», таблица `user_mcp`) — **чужой процесс**. Его нельзя путать с доверенным `mcp_strazh`.

### Как работает у нас

- В агент попадают только MCP **текущего** email из JWT. Чужой кабинет URL не видит.
- При старте учебных серверов (`entrypoint.py`) из их env **убирают** `STRAZH_MAIL_SECRET`, JWT и ключ БД. Остаётся `STRAZH_MAIL_URL`, чтобы злой плагин *мог попытаться* `POST /api/internal/deliver`.
- Internal API почты смотрит заголовок `X-Mail-Token`. Без секрета → **403** (`нет доступа к почтовому сервису`). Так устроена легенда 2: цель — письмо на `attacker@mail.ru`, факт — отказ.
- Доверенная отправка (`send_trade_email`) адреса из чата **не принимает**: получатель = email сессии. Модель этот тул не видит; письмо — после сделки с кнопки.
- Ящик `attacker@mail.ru` / `AttackerDemo1!` заводится при старте Docker **только чтобы проверить пустой inbox**, не как готовый вход в Страж.

### Зачем

Иначе «подключил плагин» = «получил ключ от всей почты стенда». Разделение: пользователь волен звать свои тулы; доставка в `mail.db` — только сервис с секретом и только на JWT.

### Что это не значит

Политика про **почту стенда и чужие ящики**, не про «любой MCP безопасен». Автор плагина не пишет в `mail.db`, но аргументы, которые модель ему отдала (свой email, остатки), у него уже есть. Четыре политики кастома — изоляция · секреты/почта · анти-SSRF · лимит писем: [КАСТОМНЫЕ_MCP.md](КАСТОМНЫЕ_MCP.md) (раздел «Итог четырёх политик»). Отчёт легенд: [МСП_легенды_отчет.md](../отчет%20по%20проделанной%20работе/МСП_легенды_отчет.md).

## 10. Демо-входов вроде `client@demo` нет

### Как работает у нас

Готовых учёток с паролем из README больше нет. Каждый регистрируется сам. Старые демо-адреса из базы при инициализации вычищаются, если всплывают.

### Зачем

Общий пароль из инструкции — дыра на любом показе. Свой пароль у каждого участника.

## Как это стыкуется в одном сценарии

1. Регистрация **почты** → сложность пароля → Argon2 → `mail.db` → cookie почты.  
2. Регистрация **Стража** → ящик на эту почту уже есть → свой пароль Стража (Argon2) → `strazh.db` → JWT.  
3. Вход в Страж → лимит по IP → Argon2 учётки → JWT. Вход в почту — пароль ящика.  
4. Чат → cookie → email из JWT → только ваш счёт.  
5. «Мои MCP» → URL в `user_mcp` на этот email; учебный плагин **без** `STRAZH_MAIL_SECRET`; `deliver` без токена → 403.  
6. Выход → `jti` в revoked.

## Краткая шпаргалка терминов

| Слово | Простыми словами |
|---|---|
| Argon2 | Надёжная «каша» из пароля |
| SQLCipher | Файл базы закрыт ключом |
| JWT | Подписанный пропуск «это вы» |
| cookie | Записка браузера, что вы вошли |
| HttpOnly | Сайт-скрипт cookie не читает |
| jti | Номер пропуска |
| revoked | Чёрный список сданных пропусков |
| `STRAZH_MAIL_SECRET` | Ключ «Страж имеет право говорить с почтой» |
| `X-Mail-Token` | Тот же секрет в заголовке internal API; без него 403 |
| Кастомный MCP | Чужой HTTP-сервер пользователя; секрета почты у него нет |
